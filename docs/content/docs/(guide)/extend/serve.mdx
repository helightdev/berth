`berth serve` offers one API over every saved host. It reaches each host the way the terminal UI does and passes the host's own operations through, so a program can use all hosts without SSH of its own. Every operation is in the [API reference](/docs/api/serve).

```bash
berth serve
```

It prints where it listens and how many hosts it knows. Only one runs per user. To use its hosts from another machine's berth, see [A berth server](/docs/use/server).

## What it adds

| Operations | For |
| --- | --- |
| [`hosts.*`](/docs/api/serve/hosts) | The saved hosts and their profiles. A host can be added, changed, removed and applied as a job. The server also renders its cloud-init seed and sends its secrets |
| [`secrets.*`](/docs/api/serve/secrets), [`registries.*`](/docs/api/serve/registries), [`settings.*`](/docs/api/serve/settings) | What the server keeps beside the hosts. A secret's value goes in and never comes back out |
| Every [berthd operation](/docs/api/host) | With a host: `"host": "NAME"` on the portal, `/v1/hosts/NAME/…` over HTTP. Only the `secrets` task is refused; `hosts.secrets` sends the server's own |
| [`jobs.*`](/docs/api/serve/jobs) | Jobs such as an apply, with their output |
| [`inbox.*`](/docs/api/serve/inbox) | Messages the hosts published on their channels and kept, taken in while `berth serve` runs; each can be marked done |
| [`kv.*`](/docs/api/serve/kv) | A key-value store with revisions, for user interfaces to keep state in |
| [`events.follow`](/docs/api/serve/events) | One stream of channel messages, jobs and key-value changes, at `/v1/events` |

All of it is also on the [portal](/docs/api/portal), the one WebSocket at `/v1/portal` for calls and streams together.

The inbox, jobs and key-value store are kept in a store in berth's data directory for `retention_days` (90 by default), and are also readable without the server:

```bash
berth inbox studio --topic ask/        # what is open; --all includes what is done
berth kv set ui layout '{"columns": 2}'
berth kv ls ui
```

## Where it listens

<Tabs items={['Unix socket', 'TCP on this machine', 'TCP for other machines']}>
<Tab value="Unix socket">

Always: `$XDG_RUNTIME_DIR/berth/serve.sock`, readable by your user only. Requests there do not need the token.

```bash
curl --unix-socket "$XDG_RUNTIME_DIR/berth/serve.sock" http://berth/v1/hosts
```

</Tab>
<Tab value="TCP on this machine">

```bash
berth serve --listen 127.0.0.1:7777
```

Requests over TCP, the portal included, send the token as a bearer. The token is made on first use and kept in `serve.token` in berth's data directory:

```bash
curl -H "Authorization: Bearer $(cat ~/.local/share/berth/serve.token)" http://127.0.0.1:7777/v1/hosts
```

A browser cannot set a header on a WebSocket, so the token is also accepted as the `Sec-WebSocket-Protocol` value.

</Tab>
<Tab value="TCP for other machines">

An address other than loopback needs `--expose` as well:

```bash
berth serve --listen 0.0.0.0:7777 --expose
```

<Callout type="warn" title="Plain HTTP">
  The connection is not encrypted, and the token gives full control of every host. Serve it behind a TLS proxy such as Tailscale Serve or Caddy, or keep it on a private network such as your tailnet.
</Callout>

</Tab>
</Tabs>

## Who gets in

A caller over TCP shows the server's token or an OAuth 2.0 access token, and acts with one of three roles. Each role includes the ones before it:

| Role | May |
| --- | --- |
| `view` | Read what the hosts and the server report, such as sessions with their output, logs, jobs and the inbox |
| `operate` | Work on the hosts with tasks, commands, terminals and files. Units, power and the key-value store are included |
| `admin` | Change profiles, secrets, registries and settings, and apply a profile to a host |

The server's token is `admin`. The socket doesn't ask for a token and is `admin` too. The [API reference](/docs/api/serve) lists the role of each operation, and [`access`](/docs/api/serve/general) tells a caller its own.

### Access tokens from an OAuth 2.0 issuer

`berth serve` can act as an OAuth 2.0 resource server. It then takes access tokens signed by an issuer you already run, such as Keycloak or Zitadel. berth doesn't keep users or sessions. The issuer decides who gets which role.

```bash title="On the server"
berth config oauth_issuer https://id.example.com/realms/main
berth config oauth_audience berth
```

| Setting | Meaning |
| --- | --- |
| `oauth_issuer` | The issuer's address, as in the tokens' `iss`. Its keys are found through its metadata |
| `oauth_audience` | The `aud` a token needs. Without it the audience is not checked |
| `oauth_claim` | The claim with the role in it, `scope` by default. Dots go into objects, as in `realm_access.roles` |
| `oauth_jwks` | The address of the issuer's keys, when its metadata is not at the usual place |
| `serve_token` | `off`: only access tokens get in, the server's own token does not |

A token is a JWT signed with one of the issuer's keys (RSA, ECDSA or Ed25519). It needs `iss` and `exp`, and the role in the claim: `berth:view`, `berth:operate` or `berth:admin`. In a claim other than `scope` the bare `view`, `operate` and `admin` count too. The highest role named is the caller's.

```bash
curl -H "Authorization: Bearer $ACCESS_TOKEN" https://berth.example.ts.net/v1/access
# {"role":"operate","setup":true,"subject":"ada"}
```

An access token is used like the server's token. It works as a bearer and as the WebSocket protocol. berth takes it as `--token` or `server_token`, and the page for a browser takes it too.

The server says which issuer it trusts at `/.well-known/oauth-protected-resource`, without a token. berth uses that to [log in](/docs/use/server#with-a-login-in-place-of-the-token) with the device grant or with client credentials.

Each of these settings can also come from the environment, as `BERTH_` and the name in capitals. That suits a container, or berth running inside another program:

```bash
docker run -d -e BERTH_OAUTH_ISSUER=https://id.example.com/realms/main \
  -e BERTH_OAUTH_AUDIENCE=berth -e BERTH_SERVE_TOKEN=off … ghcr.io/helightdev/berth
```

### Closing set-up

By default an `admin` can set the server up over the network. To keep that on the server itself:

```bash title="On the server"
berth config serve_setup off
```

A caller over TCP is then `operate` at most, and the socket stays `admin`. Some things are refused from a caller of any role:

- The settings that say who gets in and where the server's files are. `settings.set` takes only `default_host` and `retention_days`.
- A profile's `builder.link`, which is a command the server runs.
- Building a USB installer, which needs the drive.

## In a container

The `ghcr.io/helightdev/berth` image runs `berth serve --listen 0.0.0.0:7777 --expose --web` by default, as user `berth` (uid 1000):

```bash
docker run -d --name berth -p 127.0.0.1:7777:7777 \
  -v berth-config:/config -v berth-data:/data \
  -v ~/.ssh:/home/berth/.ssh:ro \
  ghcr.io/helightdev/berth
docker exec berth cat /data/berth/serve.token
```

| Path | Holds |
| --- | --- |
| `/config/berth/` | Settings and host profiles (`/config/berth/hosts`) |
| `/data/berth/` | The store, `serve.token`, the server's SSH key and builds |
| `/home/berth/.ssh` | Further SSH keys and configuration for reaching hosts |

The image contains ansible-core, the OpenSSH client and Python, so it can also apply configurations. See [A berth server](/docs/use/server) for using it from berth on another machine.

## The API documents

```bash
berth operations    # every operation, for the portal and HTTP
berth openapi       # OpenAPI 3 for the HTTP routes
berth asyncapi      # AsyncAPI 3 for the streams
```

The [API reference](/docs/api) is generated from them.
