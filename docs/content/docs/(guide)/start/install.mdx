berth runs on Linux. The program contains everything it puts on a host, so installing it means placing one file on your `PATH`. On Windows, `berth-remote` uses the hosts of a berth server.

<Tabs items={['Install script', 'Cargo', 'Container image', 'Windows']}>
<Tab value="Install script">

```bash title="Linux x86_64"
curl -fsSL https://raw.githubusercontent.com/helightdev/berth/main/install.sh | sh
```

The script downloads the latest release for Linux x86_64 from GitHub, checks it against its SHA-256 and installs it to `~/.local/bin/berth`.

| Variable | Effect |
| --- | --- |
| `BERTH_INSTALL_DIR` | Install somewhere else than `~/.local/bin` |
| `BERTH_VERSION` | Install a release tag such as `v0.2.0` instead of the latest |

On other architectures, build it with cargo.

</Tab>
<Tab value="Cargo">

Building needs Rust 1.88 or newer, Python 3 and the musl target, because the build also makes the two static programs every host gets, `berthd` and `box`:

```bash
rustup target add x86_64-unknown-linux-musl
cargo install --locked --git https://github.com/helightdev/berth berth
```

From a checkout, `cargo install --locked --path crates/berth` does the same.

</Tab>
<Tab value="Container image">

`ghcr.io/helightdev/berth` holds berth with SSH, Python and Ansible beside it. Its default command is `berth serve` on port 7777:

```bash
docker run -d --name berth -p 127.0.0.1:7777:7777 \
  -v berth-config:/config -v berth-data:/data \
  -v ~/.ssh:/home/berth/.ssh:ro \
  ghcr.io/helightdev/berth
```

Any other command goes after the image name, and the terminal UI needs the default command cleared:

```bash
docker run --rm -it -v berth-config:/config -v berth-data:/data ghcr.io/helightdev/berth list
docker run --rm -it --entrypoint berth -v berth-config:/config -v berth-data:/data \
  -v ~/.ssh:/home/berth/.ssh:ro ghcr.io/helightdev/berth
```

See [berth serve](/docs/extend/serve#in-a-container) for the volumes and the token. A berth installed on your machine can use the container's hosts with its token:

```bash
berth --server http://127.0.0.1:7777 --token "$(docker exec berth cat /data/berth/serve.token)" list
```

See [A berth server](/docs/use/server).

</Tab>
<Tab value="Windows">

berth itself needs Linux. `berth-remote` is the client for a [berth server](/docs/use/server) on another machine, with the screens of its page in a terminal:

```powershell title="PowerShell"
irm https://raw.githubusercontent.com/helightdev/berth/main/install.ps1 | iex
berth-remote --server https://berth.example.ts.net
```

The script downloads the latest release, checks it against its SHA-256 and installs it to `%LOCALAPPDATA%\Programs\berth-remote`. See [From Windows](/docs/use/server#from-windows).

</Tab>
</Tabs>

Check it:

```bash
berth --version
berth
```

## What else berth uses

| For | Needs |
| --- | --- |
| Setting up a host over SSH or applying its configuration | `ssh`, `python3`, `ansible-playbook` (ansible-core 2.21, which needs Python 3.12 or newer) |
| Building a USB installer | `python3`, `xorriso`, `curl` |
| Hashing passwords | `openssl` |
| Installing plugins from a registry | `npm` |

The install script lists what is missing. A source checkout with a `.venv` gets its own `ansible-playbook` from there:

```bash
python3 -m venv .venv && .venv/bin/pip install -r provision/requirements.txt
```

## Where berth keeps things

| What | Where |
| --- | --- |
| Settings of this machine, listed below | `~/.config/berth/config.json` |
| The other settings, registries, secret values and registry passwords | berth's store, by default `~/.local/share/berth/berth.db` |
| One profile per host, its generated passwords and the record of a machine berth created for it | berth's store too. `berth profile HOST` prints a profile and `berth credentials HOST` the passwords |
| berth's SSH keys, and the token and setup key of `berth serve` | berth's store. A key is written to `~/.local/share/berth/keys/NAME` when ssh needs it, and the token to `serve.token` |
| The key file of an encrypted store | `~/.config/berth/store.key` (setting `store_key`) |
| Locks held while berth creates or changes a host's machine | `~/.local/share/berth/locks/` |
| Your own plugins | `~/.config/berth/plugins/`, and in berth's store what reinstalls them |
| Provisioning source, unpacked from the program | `~/.local/share/berth/source/` |
| Build output such as the release archive, seeds and installer images | `~/.local/share/berth/build/` |
| Downloaded Ubuntu installer ISOs | `~/.local/share/berth/iso/` (setting `iso_dir`) |

`XDG_CONFIG_HOME` and `XDG_DATA_HOME` are honoured. `berth config` prints the paths and settings, and `berth config KEY VALUE` changes one, in the file or in the store. The Settings tab of the home screen does the same. `berth store` says where the store is and whether it is encrypted. See [The store](/docs/use/store), which also says how to restore an installation from it.

These settings stay in `config.json`, as they belong to this machine or are needed to open the store:

| Settings | What they are for |
| --- | --- |
| `store`, `store_key`, `store_ca` | Where the store is and how it is opened |
| `server`, `server_token` | The berth server this machine uses |
| `source`, `iso_dir` | Folders on this machine |

A key berth does not know stays in `config.json` as it is, such as the OAuth client settings of berth 0.4, which berth has no use for any more.

An older berth kept secrets in `secrets.json`, and registries and all settings in `config.json`. It kept each host's profile in `~/.config/berth/hosts/NAME.json`, with `NAME.credentials.json` and `NAME.instance.json` beside it. The first run of this berth moves all of them into the store. It keeps the old files in `~/.config/berth/migrated/`, and removes the copies of a berth server's profiles in `~/.local/share/berth/served/`. Delete the old files once the store has what you need. It also puts berth's own SSH key, the token of `berth serve` and your own plugins into the store, and leaves their files where they are. The setup key, which was in `serve.setup-key`, is in the store alone from then on.

<Callout type="warn">
  Profiles hold Wi-Fi passwords and enrollment keys, and the store holds generated passwords. They are in clear text unless the store is encrypted, see [The store](/docs/use/store#encrypt-it). Keep the store and its key file private, and keep files that `berth profile` writes out of version control.
</Callout>

## The provisioning source

The *provisioning source* is what berth puts on a host. It holds the Ansible role with `berthd` and `box`, the bootstrap scripts and the built-in plugins. It is built into the program and unpacked into the data directory the first time it is needed, and again after an update. The program can be copied to another machine as it is.

berth looks for the source in this order:

1. `BERTH_SOURCE`
2. the `source` setting
3. a checkout in the current directory, when berth is started inside one
4. the built-in copy

To work on the role, point berth at your checkout, and clear the setting to go back:

```bash
berth config source ~/src/berth
berth config source ""
```
