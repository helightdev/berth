berth does not have to set a machine up to work with it. A host is anything berth reaches and logs in to, and its type says what berth does with it:

| Type | What is on the host | What berth does with it |
| --- | --- | --- |
| `ssh` | Nothing of berth | Logs in over SSH for a terminal, commands and the inventory |
| `managed` | berthd and box | Also sessions, the channel, files, actions and secrets |
| `node` | A server's part of the profile: berthd, a firewall and plugin features | Also applying, roll-outs and plugin features, such as the engines that host machines ([Nodes](/docs/use/nodes)) |
| `workstation` | The whole profile | Also the desktop, the agents and the accounts, cloud seeds and the USB installer |

The type is part of the host's [profile](/docs/reference/profile#type), as `type`. A profile that doesn't say is a workstation, so older profiles mean what they always did. What the host has right now is asked of it. The overview and the Hosts tab show both when they differ, such as for a controller installed by hand.

A profile of berth 0.5 or earlier calls the type `level`, with the values `reachable`, `controller` and `workstation`. berth reads it with the names of now ([Older profiles](/docs/reference/profile#older-profiles)).

## Capabilities

| Capability | `ssh` | `managed` | `node` | `workstation` |
| --- | --- | --- | --- | --- |
| Terminal and commands over SSH, inventory | yes | yes | yes | yes |
| Install the controller alone | yes | update it | by applying | by applying |
| Sessions, channel, files, units, logs, processes | no | yes | yes | yes |
| The actions status, update and reboot | no | yes | yes | yes |
| Secrets and registry logins sent to the host | no | yes | yes | yes |
| Plugin features, their actions and services | no | no | yes | yes |
| Apply and roll-out | no | no | yes | yes |
| Cloud seed and USB installer | no | no | no | yes |
| Desktop and access links | no | no | no | yes |

The screens, the commands and the API all use the same check in berth. An action the type rules out is still listed, as unavailable, with the reason and what changes the type. Asked for anyway, the server refuses it with `501 not_available`. A roll-out leaves hosts that aren't workstations and says how many it left.

## Adding a machine that exists

A machine you can already log in to is added by its address, and berth leaves it as it is.

```bash
berth host add dock 192.0.2.4 --user ops
```

| Option | Default | For |
| --- | --- | --- |
| `--user USER` | Your SSH configuration | The SSH user |
| `--port PORT` | Your SSH configuration | The SSH port |
| `--auth AUTH` | `berth` | How berth [logs in](/docs/use/accounts#logging-in-to-hosts): `berth`, `key:NAME`, `password` or `ssh` |
| `--type TYPE` | `ssh` | The type it is meant to be |
| `--no-contact` | | Save it without logging in |

After saving the host, berth logs in the way [first contact](/docs/use/accounts#first-contact) does. It tries its own key, and if the machine refuses it, it asks for a password or a private key that logs in once to install the key. It records the host's SSH host key and prints its fingerprint. When your `~/.ssh/known_hosts` knows the address and the server runs on your machine, berth takes the host key from there. With a [berth server](/docs/use/server) elsewhere, the host is saved on the server, which logs in with its own keys and records the key the host shows it. [Host keys](/docs/use/accounts#host-keys) has more.

Then berth asks the host what it is. A machine that berth set up before has a controller that says its type, and berth offers to change the profile here when the host has more than `--type` gave. Without a terminal it prints the command.

A workstation or a node keeps its profile on the host as well. berth offers to [adopt](/docs/use/moving) it from there:

```bash
berth host adopt dock
```

A host with berth's controller alone has nothing more to keep, and berth offers to save its type:

```bash
berth host set dock type=managed
```

`berth host set HOST type=TYPE` only changes the profile here. A host's page says the same when its controller reports more than its profile says. berth refuses to install the controller alone on a host that is a workstation or a node, whatever its profile here says. It asks the host's controller first, and the playbook checks the host's own record and the profile it keeps.

In the terminal UI, create a host on the home screen and choose **Existing host, SSH only** on the **Install** tab. The address and the login are all the set-up asks for, and **Run** saves the host. For a managed host, choose **Existing host over SSH** and set **Type** to `managed`. **Run** then installs the controller.

Over the API, `hosts.save` takes a profile with only the type and `access`:

```bash
curl --unix-socket "$XDG_RUNTIME_DIR/berth/serve.sock" -X PUT \
  -d '{"type": "ssh", "access": {"address": "192.0.2.4", "user": "ops"}}' \
  http://berth/v1/hosts/dock/profile
```

The host's `trust-key` action then installs the server's key, with a password used once in its arguments ([Actions](/docs/extend/serve#actions)).

## A server for machines

A server that hosts Incus or Docker machines is a [node](/docs/use/nodes). berth applies it like a workstation, without the desktop and the accounts, and its features install the engines and register their provisioners. A server that the recipes set up before is taken in the same way.

## Installing the controller

```bash
berth run dock install-controller
```

The controller is berthd and box with the files they read, from the same part of the role that a full apply runs. Nothing else of a workstation is installed: no accounts, desktop, agents or plugins. The SSH user is the account sessions run as, and its home is where the file calls may go. The host's type becomes `managed`, and its actions are status, update, reboot and secrets.

The same is the host's action **Install the controller** on its overview, and over the API as `install-controller`. On a managed host it's called **Update the controller**: run it after updating berth, as berth's own version is all such a host is compared with. A workstation's controller comes with applying its configuration, so the action is not offered there.

berth also refuses it on a host that is a workstation or a node whatever its profile here says. It asks the host's controller first. The role checks again on the host before it changes anything. It stops when the host's record says workstation or node. It also stops when berthd there serves an account other than the SSH user. Installing the controller alone on such a host would take the workstation's controller apart. The overview and `berth action list` say when a host is more than its profile, and how to adopt it.

<Callout type="warn" title="A host without systemd">
  On a host with systemd the controller is a service that starts at boot. Without systemd, as in most containers, the controller is installed but nothing on the host starts it. berth says so and waits a minute for it to answer. The install fails when it doesn't. Something on the host then has to run `/usr/local/bin/berthd`, as the init of a container can.
</Callout>

## Changing the type

| From | To | How |
| --- | --- | --- |
| `ssh` | `managed` | Install the controller |
| `ssh` or `managed` | `node` | `berth host set HOST type=node`, list its features, and apply ([Nodes](/docs/use/nodes)) |
| `ssh`, `managed` or `node` | `workstation` | Set **Type** to `workstation` in the set-up, fill in the rest of the tabs, and apply |

berth never takes a host back to a type with less, and never removes what it installed. A node is not applied over a workstation that berth set up, as nothing would look after its desktop, agent and accounts any more. Making a profile a node's takes the fields of the agent and the operator out of it.
