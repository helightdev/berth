A command is written `berth THING ACTION [NAME] [FLAGS]`, such as `berth host show studio` or `berth secret set github`. A few that you type often have a short form. `berth --help` lists the things, and `berth THING --help` lists what each can do. The [command reference](/docs/reference/cli) has every command with its flags.

| Short form | Means |
| --- | --- |
| `berth ls` | `berth host list` |
| `berth apply HOST` | `berth host apply HOST` |
| `berth exec HOST -- COMMAND…` | Run a command on the host |
| `berth ssh HOST` | A shell over plain SSH |
| `berth run HOST ACTION` | Run one of the host's actions |
| `berth ui [HOST]` | Open [the screens](/docs/use/terminal-ui) |
| `berth serve` | `berth server run` |

`berth` alone prints a short help. A word berth doesn't know stops with status 2 and the command it was likely meant to be. A spelling of berth 0.5, such as `berth list` or `berth provision`, stops in the same way and names the command to use now.

## Which server

Each command calls the API of a berth server. berth picks the first of these:

1. `--server URL` on the command line.
2. `BERTH_SERVER` in the environment.
3. The server that `berth login` kept.
4. The `berth serve` of this machine, on its socket.
5. A server inside berth itself, with this machine's installation. This one is on Linux alone.

```bash
berth login https://berth.example.ts.net   # asks for a setup key, then keeps the server and its token
berth logout                               # forgets them again
```

The token comes from a [setup key](/docs/use/server#with-a-setup-key), from `--token-file FILE` or from `--token-stdin`. It never goes on the command line, where other users of the machine could read it. A command can also use a server once: `berth --server URL --token-file FILE ls`.

## Hosts

<Screen name="list" alt="Output of berth ls with three hosts" />

| What | Command |
| --- | --- |
| See the hosts | `berth ls` |
| See the type, address, state and actions of one host | `berth host show studio` |
| Describe a new host and install it | `berth host create studio` |
| Make the host with a provisioner | `berth host create studio --provisioner ovh-incus` |
| Take in a machine that exists | `berth host add build-vm 192.0.2.40 --user ops` |
| Change a setting | `berth host set studio hostname=studio-2` |
| Edit the profile in `$EDITOR` | `berth host edit studio` |
| Save and load the profile as JSON | `berth host export studio > studio.json`, `berth host import studio studio.json` |
| Apply the profile | `berth apply studio` |
| Bring every host that is behind up to date | `berth rollout` ([Updates](/docs/use/updates#bringing-hosts-up-to-date)) |
| Rename a host | `berth host rename studio attic` ([Renaming a host](/docs/use/moving#renaming-a-host)) |
| Take over a host from the profile it keeps | `berth host adopt studio 192.0.2.40` ([Moving a host](/docs/use/moving)) |
| Start or stop a host | `berth host start studio`, `berth host stop studio` ([Starting and stopping](/docs/use/lifecycle#starting-and-stopping)) |
| Save a copy of a host under another name | `berth host duplicate studio attic` ([Duplicating a host](/docs/use/lifecycle#duplicating-a-host)) |
| Forget a host | `berth host remove studio` |
| Forget it and destroy the machine its provisioner made | `berth host remove studio --destroy` |

`berth host create` asks what it needs to know when you're at a terminal. These are the questions of the set-up tabs of the screens, and the same rules check the answers. Each question has a flag. A script gives the answers with them:

```bash
berth host create studio --method cloud-seed --set operator_username=ops \
  --set hostname=studio --feature claude/cli --generate-passwords
```

`berth host create --help` lists every key of `--set`. With `--no-input`, or without a terminal, a missing answer stops with status 2 and names its flag.

## Installing

| What | Command |
| --- | --- |
| Write the cloud seed | `berth host seed studio > user-data`, or `--file user-data` |
| Build the USB installer | `berth host iso studio`, with `--write /dev/sdX` to write it to a drive |
| Install berth's controller alone | `berth run build-vm install-controller` ([Host types](/docs/use/types#installing-the-controller)) |
| Change the type a profile says | `berth host set build-vm type=managed` |
| Make a server a node, for Incus and Docker machines | `berth host add big 192.0.2.20 --user root --type node` ([Nodes](/docs/use/nodes)) |
| Install berth's key on a host | `berth key trust build-vm` ([First contact](/docs/use/accounts#first-contact)) |
| Check the host's SSH host key, or accept a changed one | `berth host verify studio`, `berth host verify studio --accept` |
| The passwords berth made for the accounts | `berth host credentials studio` |

For a host whose sudo takes a password, berth asks for it at the terminal, once in a command, and keeps it only while the command runs. A script gives it with `--sudo-password-stdin`, which every command takes, or keeps it as the secret `sudo/HOST`. A `berth serve` asks for it on its own terminal when it starts, or takes the kept secret.

## Jobs

What changes a host runs as a job of the server, such as an apply or a roll-out. berth follows the job with a line that shows the step it is at and the last lines of its log, and ends with one line that says how it went. `Ctrl+C` stops following. The job goes on in a `berth serve`.

| What | Command |
| --- | --- |
| Start a job and leave it running | `berth apply studio --detach`, which needs a `berth serve` |
| See the jobs | `berth job list` |
| See some of them | `berth job list --host studio`, `--subject provisioner:NAME` or `--running` |
| See the page after | `berth job list --before ID`, with the last job of the page before |
| See one job | `berth job show ID` |
| Read its log, and go on as it writes | `berth job logs ID -f` |
| Wait for it, and take its status | `berth job wait ID` |

## Actions

<Screen name="actions" alt="Output of berth action list studio, with the actions of studio and whether each can run now" />

```bash
berth action list studio                     # what the host can do
berth run studio status                      # run an action; its exit status is berth's
berth run studio backup:restore snapshot=latest -y
berth run studio claude:login                # a sign-in runs in your terminal
```

An action's arguments are `NAME=VALUE` words, and `-y` answers its question. A required argument you leave out is asked for at a terminal. `berth action list` lists berth's own actions beside the controller's, such as `install-controller`, and says why one can't run now. A host whose type is `ssh` has none of its controller's yet.

## Sessions and commands

```bash
berth exec studio -- id                      # as the agent
berth exec studio --user root -- journalctl -u berthd -n 20
berth session attach studio                  # a new shell as the agent
berth session list studio
berth session logs studio ID --tail 50 -f
berth ssh studio                             # plain SSH as the SSH user
```

<Screen name="exec" alt="Output of berth exec studio -- id, showing the agent account" />

`berth exec` ends with the command's own exit status. Its session is removed afterwards, unless `--keep` is given. `Ctrl+Q` leaves an attached terminal running.

## Secrets, registries and keys

| What | Command |
| --- | --- |
| Keep a secret | `berth secret set github`, which reads the value at a prompt or on standard input |
| Give it to a host as a variable | `berth host set studio secret.github=GH_TOKEN` |
| Give it to a host as a file | `berth host set studio secret.backup=~/.config/backup/password:0600` |
| Stop giving it | `berth host set studio secret.github=` |
| Add a registry | `berth registry add nexus nexus https://nexus.example.com --user ci-user` |
| Give its login to a host | `berth host set studio registry.nexus=on` |
| See the keys of the key ring | `berth key list` ([Keys](/docs/use/accounts#keys)) |
| Replace a key on the hosts that take it | `berth key rotate berth` ([Rekeying](/docs/use/accounts#rekeying)) |

## Ports, services and messages

| What | Command |
| --- | --- |
| Reach a port of a host from this machine | `berth port forward studio 8080`, or `8080:3000` for another local port |
| Call a service a plugin runs | `berth service call studio notes/store list` |
| Read a host's channel as it comes | `berth channel listen studio` |
| The messages the server took in | `berth inbox list` |
| Mark one done, or open again | `berth inbox done studio ID`, `berth inbox reopen studio ID` |
| The server's key-value store | `berth kv list NAMESPACE`, `berth kv set NAMESPACE KEY JSON` |

## In scripts

| Flag | What it does |
| --- | --- |
| `-o json` | Print the API's own JSON documents instead of tables. Errors go to standard error as JSON as well |
| `--no-input` | Never ask; a missing value stops with status 2 and names its flag |
| `-y` | Answer yes to every question |
| `-q` | Print only the result |
| `--color never` | Print without colours, as `NO_COLOR` does |

| Status | Means |
| --- | --- |
| 0 | Done |
| 1 | A job failed, or a host didn't answer |
| 2 | The command line was wrong |
| 3 | Refused. The role is too low, the host or the server can't do it now, or a question had the answer no |
| 4 | The server couldn't be reached |

`berth completion bash` prints the completions of a shell. Source them from its start-up file:

```bash
echo 'source <(berth completion bash)' >> ~/.bashrc
```
