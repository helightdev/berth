`berth --help` prints the full list. Commands that take a `HOST` accept a saved host's name or a path to a profile.

With a [berth server](/docs/use/server) set, by `--server` or the `server` setting, the host commands use the server's hosts. Installing, secrets and registries then stay on the server.

## Hosts and profiles

| Command | Does |
| --- | --- |
| `berth` | The home screen |
| `berth HOST` | Open a host in the terminal UI; a new name starts a new profile |
| `berth list` | Saved hosts and their addresses |
| `berth host add NAME ADDRESS [--user USER] [--port PORT] [--auth AUTH] [--level LEVEL] [--no-contact]` | Save a machine that exists by its address, reachable unless `--level` says otherwise, and install berth's key there ([Host levels](/docs/use/levels#adding-a-machine-that-exists)) |
| `berth profile HOST` | The host's profile, as JSON on standard output |
| `berth profile HOST --set FILE` | Save the profile in FILE as the host's, checked as the terminal UI reads one. `-` reads standard input. With a [berth server](/docs/use/server) set, it is saved on the server |
| `berth credentials HOST [--show]` | The passwords berth generated for the host's accounts, an account and its password to a line. Only to a terminal unless `--show` is given. For a server's host they come from the server |
| `berth inventory [HOST…]` | The hosts as an Ansible inventory |
| `berth config` | Where things are kept, and the settings |
| `berth config KEY [VALUE]` | Change a setting; no value clears it |
| `berth --version` | The version |
| `berth --server URL [--token TOKEN] [COMMAND…]` | Run once with the hosts of a berth serve elsewhere ([A berth server](/docs/use/server)) |

## Installing

| Command | Does |
| --- | --- |
| `berth iso HOST [--write /dev/sdX]` | Build the USB installer, downloading the ISO if none is set; write it to a drive after asking |
| `berth seed HOST` | Render the cloud-init seed |
| `berth apply HOST` | Apply the host's profile to it over SSH. With a [berth server](/docs/use/server) set, as a job there. Only a workstation is applied |
| `berth host install HOST` | Install berth's controller alone on a host below a workstation ([Installing the controller](/docs/use/levels#installing-the-controller)) |
| `berth host level HOST LEVEL` | Save the level the host's profile says, such as for a host with berth's controller added by its address. A workstation is adopted instead ([Adding a machine that exists](/docs/use/levels#adding-a-machine-that-exists)) |
| `berth apply --behind [--update] [--reboot [--force]]` | Apply every host that is behind, one at a time ([Updates](/docs/use/updates#bringing-hosts-up-to-date)). `--all` takes the current ones too |
| `berth remove HOST` | Forget a host. The machine itself is left as it is, and a machine berth created for the host must be deleted first |
| `berth adopt HOST [[USER@]ADDRESS] [--port PORT] [--key FILE] [--force]` | Save a host from the profile it keeps, read over SSH with sudo. Without an address, a saved host by its own ([Moving a host](/docs/use/moving)) |
| `berth key` | The SSH keys of berth's [key ring](/docs/use/accounts#keys), with their public halves, the hosts that use each, and what is being replaced. With a berth server set, the server's |
| `berth key new NAME`, `berth key add NAME FILE\|-` | Make a key, or take in a private key from a file or standard input |
| `berth key show [NAME]`, `berth key remove NAME` | Print a public half, the key `berth`'s by default. Remove a key, which berth refuses while a host logs in with it |
| `berth key rotate [NAME]` | Replace a key on the hosts that take it ([Rekeying](/docs/use/accounts#rekeying)) |
| `berth key trust HOST [--key FILE] [--keep-password]` | Install the host's key with a password or a key used once ([First contact](/docs/use/accounts#first-contact)) |
| `berth key host HOST [--accept]` | The host's recorded SSH host key; accept a changed one |
| `berth connect URL` | Use the [berth server](/docs/use/server#with-a-setup-key) at URL, with the token a setup key collects. The key comes on standard input |
| `berth publish REGISTRY[/REPOSITORY] [HOST [--login [REGISTRY]]]` | Upload the release archive and use it as HOST's release address ([Registries](/docs/use/registries#publishing-the-release-archive)) |
| `berth image push REGISTRY[/REPOSITORY] [TAG]` | Push the container image |

Both build commands refuse to start while the profile has problems, and list them.

## Machines, provisioners and resources

| Command | Does |
| --- | --- |
| `berth provisioner` | The registered provisioners, and whether each can be used here |
| `berth provisioner types` | The types of provisioner the plugins bring, such as `incus/vm` |
| `berth provisioner add NAME TYPE [SETTING=VALUE…]` | Register a provisioner of a type under a name of its own, with its settings ([Provisioners](/docs/deploy/provisioners#register-a-provisioner)) |
| `berth provisioner remove NAME` | Forget a provisioner that doesn't hold anything, with its settings and its own secrets |
| `berth provisioner NAME [SETTING=VALUE…]` | How it is now, what it can do, and what berth made with it, by kind. Each `NAME=VALUE` sets one of the provisioner's own arguments for this call alone |
| `berth provisioner NAME actions` | Its actions, with their arguments |
| `berth provisioner NAME run ACTION [NAME=VALUE…] [--yes]` | Run one. `settings` keeps the values of its own arguments, `secrets` its own secrets, and `new-deployment` makes a deployment. One that changes something runs as a job, and berth ends with its exit code |
| `berth provisioners` | The registered provisioners, and what each asks for |
| `berth resource [--provisioner NAME] [--kind KIND] [--host HOST]` | What provisioners made for berth, such as machines and deployments, as berth's records have them ([Resources](/docs/deploy/resources)) |
| `berth resource ID` | One of them, as its provisioner says it is now, with its actions. A name works while only one resource has it |
| `berth resource ID actions` | Its actions, with their arguments |
| `berth resource ID run ACTION [NAME=VALUE…] [--yes]` | Run one, such as `start`, `stop` or an action of its kind |
| `berth resource ID logs [--tail N] [--follow]` | What it wrote, as its provisioner gives it |
| `berth resource ID change [--spec FILE\|-] [--secret NAME[:VARIABLE]]… [NAME=VALUE…]` | Give it other values, a new specification or other secrets. The rest stays as it is |
| `berth resource ID remove [--yes]` | Remove it with its provisioner and forget it. A host's profile stays |
| `berth deploy NAME --provisioner PROVISIONER --spec FILE\|- [--secret NAME[:VARIABLE]]… [--token TEXT] [NAME=VALUE…]` | Make a deployment from a specification, such as a Compose file. With the name of one that exists, change it ([Deployments](/docs/deploy/deployments)) |
| `berth provision HOST PROVISIONER [NAME=VALUE…] [--yes]` | Create the machine for a saved host and set it up |
| `berth instance HOST` | The machine berth created for the host, as `berth resource ID` shows it |
| `berth instance HOST start\|stop` | Start or stop it, when the provisioner can |
| `berth instance HOST destroy [--yes]` | Delete the machine, after you type the host's name. The profile stays |

With a [berth server](/docs/use/server) set, the server's provisioners, plugins and resources are used. Changing a resource needs the role `admin`, reading its log `operate`, and an action of a provisioner or a resource its own role. See [Provisioners](/docs/deploy/provisioners) and [Resources](/docs/deploy/resources#with-a-berth-server).

## Tasks

```bash
berth tasks studio                       # what the host can do
berth run studio status                  # run a task; its exit code is berth's
berth run studio backup:restore snapshot=latest --yes
berth run studio claude:login            # a sign-in runs in your terminal
```

`berth run HOST TASK` runs a task and its plugin steps and leaves with the task's exit code. A task's arguments are given as `NAME=VALUE`, and `--yes` answers its confirmation. `berth manage HOST TASK` is the same command. Tasks that need a terminal, such as sign-ins, run in your terminal over `ssh -t`.

`berth tasks` lists berth's own actions beside the host's tasks, such as `install-controller`, and says why one cannot run now. A host that is only reachable has no tasks yet.

When a [berth server](/docs/use/server) keeps the host, `berth tasks` lists the server's actions for the host: its tasks, and berth's own such as `apply` and `seed`. `berth run` runs any of them through the server, which keeps a job of each run ([Actions](/docs/extend/serve#actions)).

## Sessions and commands

```bash
berth exec studio -- id                  # as the agent
berth exec studio --user root -- journalctl -u berthd -n 20
berth attach studio                      # a new shell as the agent
berth sessions studio
berth output studio ID --tail 50 --follow
```

<Screen name="exec" alt="Output of berth exec studio -- id, showing the agent account" />

| Command | Does |
| --- | --- |
| `berth exec HOST [--user agent\|operator\|root] [--keep] -- COMMAND…` | Run a command on the host and leave with its exit code. The session is removed afterwards unless `--keep` is given |
| `berth attach HOST [ID]` | Put this terminal onto a terminal session of the host, or onto a new shell as the agent; Ctrl+Q leaves it running |
| `berth sessions HOST` | The host's sessions, running and ended |
| `berth output HOST ID [--tail N] [--follow]` | What a session wrote |
| `berth ssh HOST [COMMAND]` | A shell over plain SSH as the SSH user, or one command |
| `berth ssh HOST --agent` | The same as the agent account |

## Secrets and registries

| Command | Does |
| --- | --- |
| `berth secret [set NAME \| remove NAME]` | Secret values, kept in berth's store |
| `berth host HOST` | The secrets and registries a host gets |
| `berth host HOST secret NAME env VARIABLE \| file PATH [MODE] \| off` | Give a secret to a host, or stop |
| `berth host HOST registry NAME on\|off` | Give a registry's login to a host, or stop |
| `berth registry` | The registries |
| `berth registry add NAME nexus\|npm\|raw\|docker URL [USERNAME]` | Add one |
| `berth registry repo NAME npm\|raw\|docker REPOSITORY [HOST[:PORT]]` | Add a repository to a Nexus server |
| `berth registry login NAME` | Store its password or token |
| `berth registry check [NAME]` | Whether it answers and accepts the login |
| `berth registry remove NAME` | Remove it |

<Screen name="host" alt="Output of berth host studio: two secrets, one registry" />

See [Secrets](/docs/use/secrets) and [Registries](/docs/use/registries).

## Plugins

| Command | Does |
| --- | --- |
| `berth plugins` | Plugins and where they come from |
| `berth plugins add SPEC` | Install a plugin with npm from a name, a tarball or a folder |
| `berth plugins remove NAME` | Remove one of yours, by its id or npm name |
| `berth plugins update --check` | Which of yours have a newer version in their registry |
| `berth plugins update [ID] [--apply [--reboot [--force]]]` | Update one plugin or all, then list the hosts that are behind. `--apply` brings them up to date |

With a [berth server](/docs/use/server) set, these show and change the server's plugins. A `.tgz` or folder named in `add` is sent from your machine.

## Services, channel and the local API

| Command | Does |
| --- | --- |
| `berth call HOST SERVICE METHOD [JSON]` | Call a service a plugin runs on the host |
| `berth channel HOST [TOPIC-PREFIX] [--since ID]` | Messages on the host's channel as they come |
| `berth serve [--listen ADDRESS:PORT [--expose] [--web]]` | The API over all hosts ([berth serve](/docs/extend/serve)). `--expose` allows an address other than loopback. `--web` also shows [the hosts in a browser](/docs/use/server#in-a-browser) |
| `berth update [--check]` | Replace this program with the latest release ([Updates](/docs/use/updates#berth-itself)) |
| `berth setup-key [--remove]` | Make a [setup key](/docs/use/server#with-a-setup-key) for the `berth serve` whose data is on this machine, valid for 24 hours, in place of any earlier one. `--remove` ends it |
| `berth inbox [HOST] [--topic PREFIX] [--all]` | Messages `berth serve` took in from the hosts' channels |
| `berth kv get\|set\|rm\|ls NAMESPACE [KEY] [JSON]` | The key-value store of `berth serve` |
| `berth store` | Where the store is, and whether its state is encrypted ([The store](/docs/use/store)) |
| `berth store encrypt\|rekey\|decrypt [--yes]` | Seal the store's state with a new key file, change the key, or write it plain again. Stop `berth serve` first |
| `berth store copy TARGET\|-\|--target-file FILE [--into-existing]` | Copy the store into another SQLite file or PostgreSQL database ([Move to another database](/docs/use/store#move-to-another-database)). `-` reads a URL from standard input, which keeps its password out of the process list |
| `berth operations`, `berth openapi`, `berth asyncapi` | The API documents of `berth serve` ([API](/docs/api#the-documents)) |
