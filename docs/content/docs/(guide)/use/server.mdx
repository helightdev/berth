A server machine keeps the hosts with their profiles and secrets, and runs `berth serve`. berth on another machine, such as your laptop, then uses that server's hosts instead of its own: the terminal UI, `berth list`, `berth run` and the other host commands go through the server's [portal](/docs/api/portal).

```text
 your laptop                  the server                       hosts
┌─────────────┐  HTTPS/HTTP  ┌───────────────────────────┐ SSH ┌─────────┐
│ berth       │ ───────────▶ │ berth serve               │ ──▶ │ studio  │
│ --server …  │   + token    │ profiles, secrets, builds │ ──▶ │ cloud-1 │
└─────────────┘              └───────────────────────────┘     └─────────┘
```

## Run the server

The server needs SSH access to the hosts. The container image is the shortest way:

```bash title="On the server"
docker run -d --name berth -p 127.0.0.1:7777:7777 \
  -v berth-config:/config -v berth-data:/data \
  -v ~/.ssh:/home/berth/.ssh:ro \
  ghcr.io/helightdev/berth
docker exec berth cat /data/berth/serve.token
```

Without the image, run `berth serve --listen 0.0.0.0:7777 --expose` where berth is installed. The token is in `~/.local/share/berth/serve.token`. Set the hosts up on the server as usual, with the terminal UI there or `docker run --rm -it --entrypoint berth …` for the container.

The server keeps its state in one store, a SQLite file by default. [The store](/docs/use/store) says how to keep it in PostgreSQL, encrypt it and restore the server on another machine from it.

<Callout type="warn" title="Put TLS in front">
  `berth serve` speaks plain HTTP, and the token gives full control of every host. Serve it behind a TLS proxy, such as Tailscale Serve or Caddy, and use the `https://` address. Without one, keep the port on loopback or a private network such as your tailnet.
</Callout>

With Tailscale on the server:

```bash title="On the server"
sudo tailscale serve --bg --https=443 http://127.0.0.1:7777
```

## Connect to it

<Tabs items={['Try it once', 'Every time']}>
<Tab value="Try it once">

`--server` and `--token` apply to one run and leave your own hosts and settings alone:

```bash
berth --server https://berth.example.ts.net --token "$(cat token)"         # the terminal UI
berth --server https://berth.example.ts.net --token "$(cat token)" list
berth --server https://berth.example.ts.net --token "$(cat token)" run studio status
```

</Tab>
<Tab value="Every time">

Store the address and token as settings, and berth uses the server on every run:

```bash
berth config server https://berth.example.ts.net
berth config server_token "$(cat token)"
berth config server ""            # back to the hosts of this machine
```

`BERTH_SERVER` and `BERTH_TOKEN` in the environment take precedence over the settings.

</Tab>
</Tabs>

### With a setup key

A setup key lets the first user collect the token without reading `serve.token` on the server. Whoever installs the server, such as a coding agent, hands on the key and never sees the token. Make one where the server keeps its data:

```bash title="On the server"
docker exec berth berth setup-key       # or: berth setup-key
```

It prints the key. On your own machine, give it to berth when it asks:

```bash
berth connect https://berth.example.ts.net
```

berth checks the key, collects the token and saves `server` and `server_token`. Or open the server's page with the key in the link:

```text
https://berth.example.ts.net/#setup-key=KEY
```

The page signs the browser in and shows the token, with the two `berth config` commands for a terminal. The key lasts 24 hours. It ends sooner when you choose **Done** on the page, or when `berth connect` has saved the token. Until then it's as good as the token, so keep it to yourself. A new key replaces the old one, and `berth setup-key --remove` ends it. A server with `serve_token` off has no token to hand out, so it doesn't make a key.

| Address | Reaches |
| --- | --- |
| `https://HOST[:PORT]` | A server behind a TLS proxy |
| `http://HOST:PORT` | A server's port directly |
| `unix:/path/to/serve.sock` | A `berth serve` on this machine, without a token |

## In a browser

With `--web`, `berth serve` also shows its hosts as a page. It needs the build of berth with the page in it. The container image is one, and the install script takes it with `BERTH_VARIANT=web` ([Building](/docs/reference/building#with-the-page-for-a-browser)).

```bash title="On the server"
berth serve --listen 0.0.0.0:7777 --expose --web
```

Open the server's address in a browser and enter the token:

```
https://berth.example.ts.net/
https://berth.example.ts.net/#token=TOKEN     # a link that signs in
```

To open the page on a phone, choose **Open on another device** on the Settings tab of the home screen. It shows a QR code and the link with the token in it, so anyone who scans it gets in. The row is there when berth reaches the server with its token, such as `server_token`, and in the page for the role `admin`. From the terminal UI the link opens the server's own page, which needs `--web`. From the page it opens the same page you are on, such as the one at /web.

The page is the terminal UI drawn in the browser. It has the host list and the overview of each host, where tasks run and sessions open in the terminal panel. The browser keeps the token until **o** on the host list signs out. A token in a link is taken out of the address bar when the page opens.

With the role `admin` the page also sets the server up, with the same screens as the terminal UI:

- **Provisioners**, **Settings**, **Registries**, **Secrets** and **Plugins** are tabs of the home screen. On **Plugins**, `u` sends a `.tgz` from the device. A provisioner's page opens the pages of what berth made with it ([Resources](/docs/deploy/resources#in-the-terminal-ui)).
- **New host** starts a profile, and a host's overview opens its Install, Features, Settings and Run tabs. A new host opens on Install with **Create a machine** chosen, and offers only Create a machine, Cloud-init seed and Existing host over SSH.
- **Run** does what the chosen method does on the server. That is creating the machine, a cloud-init seed to copy, or an apply over SSH. The output is shown as it runs.
- **Install secrets and registry logins** sends a host what its profile names.

Some keys differ:

| In the page | Instead of |
| --- | --- |
| **Alt+Q** leaves a running session | `Ctrl+Q`, which closes some browsers |
| **Ctrl+V** and the browser's paste | The desktop clipboard tools |
| A click on a link opens a tab | `xdg-open` |
| **g** generates and **p** takes a password to hash | `F4` and `F5`, which reloads a page |

A password the server makes up is shown once in the page. The server keeps a copy in its store, and `berth credentials HOST` shows it again to an admin of the server.

What needs your own machine stays in the terminal UI. That is the USB installer and the container image, values read from your local keys, and sending a plugin's folder.

Keys the browser keeps for itself, such as `Ctrl+W` and `Ctrl+T`, never reach a shell in the page. A phone can tap rows and key hints, but has no keyboard for a terminal.

### Without `--web`

The same page is part of this site, at [/web](/web/). It asks which server to use, or takes it from its address:

```
/web/?server=https://berth.example.ts.net
/web/?server=https://berth.example.ts.net#token=TOKEN
```

Your browser talks to the server you name, and to nothing else. It keeps the server and the token. A page loaded over `https` can only reach a server over `https`.

## From Windows

berth runs on Linux. On Windows, `berth-remote` uses the hosts of a server from a terminal. It shows the screens of the page in a terminal, and works with a server that runs without `--web`. Install it in PowerShell:

```powershell
irm https://raw.githubusercontent.com/helightdev/berth/main/install.ps1 | iex
```

The script downloads the latest release, checks it against its SHA-256 and installs it to `%LOCALAPPDATA%\Programs\berth-remote`. `BERTH_INSTALL_DIR` and `BERTH_VERSION` work as for `install.sh`. To download it by hand, take `berth-remote-x86_64-windows.zip` and its `.sha256` file from the [latest release](https://github.com/helightdev/berth/releases/latest).

Start it in Windows Terminal, or in the console of Windows 10 or later:

```powershell
berth-remote --server https://berth.example.ts.net
```

It asks for the token and keeps the server and the token in `%APPDATA%\berth-remote` for the next run. A token never goes on the command line:

| Variable or option | Effect |
| --- | --- |
| `BERTH_TOKEN` | The token, so it isn't asked for |
| `BERTH_SETUP_KEY` | A [setup key](#with-a-setup-key), which collects the token |
| `BERTH_SERVER` | The server, instead of `--server` |
| `--forget` | Keep the server and the token for this run only |

The screens and keys are those of the page. **Ctrl+Q** quits, and `u` on **Plugins** opens the file dialog of Windows. berth-remote also builds on Linux and macOS:

```bash
cargo install --locked --git https://github.com/helightdev/berth berth-remote
```

## What works from another machine

| Works through the server | Stays on a machine with the host's profile |
| --- | --- |
| `berth list`, and the host list of the home screen and of the page | USB installers: `berth iso` and writing a drive |
| The host's overview with its tasks, sessions and terminal panel | Applying to this machine or an inventory, and container images |
| The host commands such as `berth run`, `exec`, `attach` and `channel` | Publishing a release or an image by hand |
| The set-up tabs of a host, new hosts, and `berth remove` | |
| `berth profile` and `berth credentials` | |
| `berth apply`, `berth seed`, and the **Secrets and registry logins** task | |
| `berth provisioner`, `berth provision`, `berth instance`, `berth resource` and `berth deploy` | |
| `berth secret`, `berth registry` and `berth host` | |
| The Plugins tab and `berth plugins` | |

berth keeps the server's hosts apart from its own. Its own hosts are hidden while a server is set and return when the setting is cleared.

### Setting the server up from here

With the role `admin` on the server, which its token has, berth sets the server up as if the hosts were its own. What you change is saved on the server:

- A host's set-up tabs, a new host from the home screen, and `berth profile HOST --set FILE` save the profile there.
- A password generated on the set-up tabs is made and kept by the server. `berth credentials HOST` asks the server for it.
- **Apply this configuration** and `berth apply HOST` run as a job on the server. Its output is shown as it comes.
- `berth seed HOST` has the server render the cloud-init seed, and writes it here.
- `berth provision HOST` and `berth instance HOST` use the server's provisioners and secrets, and create the machine from the server ([Provisioners](/docs/deploy/provisioners#with-a-berth-server)). `berth provisioner` shows the server's provisioners, and their actions run there.
- `berth resource` and `berth deploy` use the server's resources. A deployment's specification is sent to the server and kept there, and it gets the server's secrets ([Deployments](/docs/deploy/deployments#with-a-berth-server)).
- A secret's value is sent to the server and kept only there. Here berth knows its name.
- The `tailnet_` settings and the secret `tailnet_api_key` are the server's, which creates the [enrollment keys](/docs/use/access#automatic-enrollment-keys) for its hosts. Settings and `berth config` change them there.
- A plugin is installed on the server, and its features show on the Features tab of the server's hosts. A `.tgz` or folder of yours is sent there first.
- The server logs in to hosts with the keys of [its own key ring](/docs/use/accounts#keys), by default its key `berth`, which a host it installs takes. `berth key` and its commands act on the server's ring, and its private halves stay there. For a host that was set up elsewhere, add the key `berth` to the operator first. Settings lists the keys and copies one to the clipboard, and **Log in with** on a host's Install tab chooses among them.
- `berth key rotate` replaces a key of the server's on the hosts that take it, as a job of the server ([Rekeying](/docs/use/accounts#rekeying)). First contact and accepting a changed host key are done on the server, with `berth key trust HOST` and `berth key host HOST --accept` there.

With a lesser role the set-up tabs say *This host is set up on the berth server at URL*, and the host's overview works as before. The roles, access tokens of an OAuth 2.0 issuer in place of the token, and how to keep set-up on the server itself are in [berth serve](/docs/extend/serve#who-gets-in).
