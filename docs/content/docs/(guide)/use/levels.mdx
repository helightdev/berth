berth does not have to set a machine up to work with it. Each host has one of three levels:

| Level | What is on the host | What berth does with it |
| --- | --- | --- |
| `reachable` | Nothing of berth | Logs in over SSH for a terminal, commands and the inventory |
| `controller` | berthd and box | Also sessions, the channel, files, tasks and secrets |
| `workstation` | The whole profile | Also the desktop, the agents, plugins, applying and roll-outs |

The level is part of the host's [profile](/docs/reference/profile#level), as `level`. A profile that doesn't say is a workstation, so profiles from before levels mean what they always did. What the host has right now is asked of it. The overview and the Hosts tab show both when they differ, such as for a controller installed by hand.

## Capabilities

| Capability | `reachable` | `controller` | `workstation` |
| --- | --- | --- | --- |
| Terminal and commands over SSH, inventory | yes | yes | yes |
| Install the controller alone | yes | update it | by applying |
| Sessions, channel, files, units, logs, processes | no | yes | yes |
| The tasks status, update and reboot | no | yes | yes |
| Secrets and registry logins sent to the host | no | yes | yes |
| Plugin features, their tasks and services | no | no | yes |
| Apply, roll-out, cloud seed, USB installer | no | no | yes |
| Desktop and access links | no | no | yes |

The terminal UI, the browser page, the commands and the API all use the same check in berth. An action the level rules out is still listed, as unavailable, with the reason and what raises the level. Asked for anyway, the server refuses it with `501 not_available`. A roll-out leaves hosts that aren't workstations and says how many it left.

## Adding a machine that exists

A machine you can already log in to is added by its address, and berth leaves it as it is.

```bash
berth host add dock 192.0.2.4 --user ops
```

| Option | Default | For |
| --- | --- | --- |
| `--user USER` | Your SSH configuration | The SSH user |
| `--port PORT` | Your SSH configuration | The SSH port |
| `--auth AUTH` | `berth` | How berth [logs in](/docs/use/accounts#logging-in-to-hosts): `berth`, `key:NAME`, `password` or `ssh` |
| `--level LEVEL` | `reachable` | The level it is meant to have |
| `--no-contact` | | Save it without logging in |

After saving the host, berth logs in the way [first contact](/docs/use/accounts#first-contact) does. It tries its own key, and if the machine refuses it, it asks for a password or a private key that logs in once to install the key. It records the host's SSH host key and prints its fingerprint. When your `~/.ssh/known_hosts` knows the address, berth takes the host key from there. With a [berth server](/docs/use/server) set, the host is saved on the server, which logs in with its own keys.

Then berth asks the host what it is. A machine that berth set up before has a controller that says its level, and berth offers to change the profile here to a higher one than `--level` gave. Without a terminal it prints the command.

A workstation has its whole profile on the host as well. berth offers to [adopt](/docs/use/moving) it from there:

```bash
berth adopt dock
```

A host with berth's controller alone has nothing more to keep, and berth offers to save its level:

```bash
berth host level dock controller
```

`berth host level HOST LEVEL` only changes the profile here. A host's page says the same when its controller reports more than its profile says. berth refuses to install the controller alone on a host that is a workstation, whatever its profile here says. It asks the host's controller first, and the playbook checks the host's own record and the profile it keeps.

In the terminal UI, create a host on the home screen, choose **Existing host over SSH** on the **Install** tab and set **Level**. Below a workstation, the address and the login are all the set-up asks for. **Run** then installs the controller for a controller host and saves a reachable one. The browser page does the same through the server.

Over the API, `hosts.save` takes a profile with only the level and `access`:

```bash
curl --unix-socket "$XDG_RUNTIME_DIR/berth/serve.sock" -X PUT \
  -d '{"level": "reachable", "access": {"address": "192.0.2.4", "user": "ops"}}' \
  http://berth/v1/hosts/dock/profile
```

The host's `trust-key` action then installs the server's key, with a password used once in its arguments ([Actions](/docs/extend/serve#actions)).

## Add the server to berth

The recipes leave a plain Ubuntu server where the account `root` takes the public key you gave `rescue-install`. Add it to berth from your own machine. This example uses the made-up name `big` and the address `192.0.2.20`:

```bash
berth host add big 192.0.2.20 --user root --auth ssh
berth host install big
```

`berth host add` saves `big` as a reachable host. `--auth ssh` makes berth log in with your own SSH configuration and agent, so the key that works for `ssh root@192.0.2.20` works for berth. The default, `--auth berth`, uses berth's own key, which berth installs on the first contact with a password or a private key that logs in once. `--auth ssh` works with a local berth only. With a [berth server](/docs/use/server) set, the server logs in with its own keys.

`berth host install big` puts the controller alone on the server. berth can then report its status and run commands there, and it can update and reboot the server. Sessions run as the SSH user, here `root`. berth does not apply such a server as a workstation. It stays a reachable or controller host, and the machines on it are created with the Incus or Docker provisioner.

The recipes are in [`recipes/`](https://github.com/helightdev/berth/tree/main/recipes): `rescue-install` installs Ubuntu, and `incus-host` makes the server a host for machines.

## Installing the controller

```bash
berth host install dock
```

The controller is berthd and box with the files they read, from the same part of the role that a full apply runs. Nothing else of a workstation is installed: no accounts, desktop, agents or plugins. The SSH user is the account sessions run as, and its home is where the file calls may go. The host's level becomes `controller`, and its tasks are status, update, reboot and secrets.

The same is the host's action **Install the controller** on its overview, in the browser page and over the API as `install-controller`. On a controller host it's called **Update the controller**: run it after updating berth, as berth's own version is all such a host is compared with. A workstation's controller comes with applying its configuration, so the action is not offered there.

berth also refuses it on a host that is a workstation whatever its profile here says. It asks the host's controller first. The role checks again on the host before it changes anything. It stops when the host's record says workstation. It also stops when berthd there serves an account other than the SSH user. Installing the controller alone on such a host would take the workstation's controller apart. The overview and `berth tasks` say when a host is more than its profile, and how to adopt it.

<Callout type="warn" title="A host without systemd">
  On a host with systemd the controller is a service that starts at boot. Without systemd, as in most containers, the controller is installed but nothing on the host starts it. berth says so and waits a minute for it to answer. The install fails when it doesn't. Something on the host then has to run `/usr/local/bin/berthd`, as the init of a container can.
</Callout>

## Raising a level

| From | To | How |
| --- | --- | --- |
| `reachable` | `controller` | Install the controller |
| `reachable` or `controller` | `workstation` | Set **Level** to `workstation` in the set-up, fill in the rest of the tabs, and apply |

berth never lowers a level, and never removes what it installed.
