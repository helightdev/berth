## What updates itself

Ubuntu security updates and Firefox's vendor updates install automatically. The host never reboots on its own. **Status** says when a reboot is needed.

## What you update

| How | Updates |
| --- | --- |
| **Update** on the overview, or `berth run HOST update` | `apt` update and `dist-upgrade`, then Claude Code, Codex, Pi, T3 Code and the Unity CLI to their latest versions, through their plugins |
| **Reboot**, or `berth run HOST reboot` | Restarts the host to finish updates |
| **Apply this configuration** | Runs the role again, which brings new or changed features and settings, berthd and box, and plugin tasks and services |
| `berth plugins update` | Your plugins, to the latest version of their registry ([Updating a plugin](/docs/extend/plugins#updating-a-plugin)) |

The versions in the defaults (`devbox_claude_version`, `devbox_codex_version`, `devbox_pi_version`, `devbox_t3_version`) are the least ones, so applying the configuration again does not go back to them after an update. Claude Code's own self-update is off.

## berth itself

```bash
berth update --check     # is there a newer release?
berth update             # download it, check its SHA-256 and replace this program
```

`berth update` takes the same archive as the install script. It offers only full releases, not pre-releases such as `0.4.0-rc.1`, and moves from a pre-release to its release. A container is updated by pulling a newer image. `berthd` and `box` travel inside `berth`. A host gets the new ones when you apply its configuration. Its overview says when its tools are of another version than your berth. `BERTH_RELEASES` names a mirror of the releases page.

## Hosts that are behind

Applying records on the host which berth and which plugins the configuration came from, with each plugin's version and a digest of its files. berth compares that with what it would apply now. When a plugin was updated, or berth was, the overview says what changed, such as `claude 1.0.0 → 1.1.0`. A plugin that changed without a new version shows as `(changed)`. A berth server's host list marks such a host `behind`, and `hosts.get` says what changed.

A host applied by an older berth, or with an older berthd, says nothing yet. Applying it once with this berth records it.

## Bringing hosts up to date

```bash
berth apply --behind                     # every host that is behind
berth apply --behind --update --reboot   # and run Update, and reboot where needed
berth plugins update --apply             # update the plugins, then the same
```

The hosts are taken one at a time, by name. Each is applied and then checked. Its berthd has to answer with this berth's version and the host must no longer be behind. Its Status task has to end well too. Hosts that are current are skipped. The first host that fails stops the roll-out, and the hosts after it are not touched.

| Option | Does |
| --- | --- |
| `--update` | Runs the host's Update task after applying. If it ends badly, that host is finished and the roll-out stops after it |
| `--reboot` | Reboots a host that says it needs it, waits up to ten minutes for it to answer again, then checks it. A host with running sessions is not rebooted, and the roll-out stops there |
| `--force` | Reboots also while sessions run, which ends them |
| `--all` | Applies the hosts that are current too |

With a berth server set, the roll-out is a job of the server. On the Plugins tab, after an update, `r` lists the hosts with what changed and starts on a second `r`. `R` does the same with `--reboot`.

## What applying again keeps

Applying again keeps the agent's home and workspaces, sign-ins, the secrets that were sent, running sessions, and the channel's messages. A tool installed at a newer version than the profile names stays at that version. A plugin service restarts only when its script or unit changed, and the output says which.

A task, service or channel topic a plugin no longer has is gone after applying. What a plugin's own Ansible tasks installed stays on the host.

## After changing versions

Applying does not restart desktops that are already running or turns an agent is in the middle of. After changing versions, a service's environment or unit files, restart the agent's user services in a quiet moment, or reboot.

Applying restarts berthd only when its program or unit changed, because a restart ends the sessions it holds. New tasks, services and channel topics only need a reload, which applying does.

## What berth does not do

- The bootstrap retries an install that did not finish, but it does not pull Git branches or replace a release that completed. A host changes when you apply the role again.
- No automatic firmware updates, encrypted unattended boot, swap tuning, offline package bundles, or transactional updates with rollback.
- Laptop power settings are defaults for fresh physical installs. Settings the user changed in XFCE win. Reboot after the first laptop setup.

## Data

Application data is stored under `/home/agent` and `/srv/agent`. Back both up before upgrades, with the [Backup plugin](/docs/use/backups) or your own tools.
