Every host has two accounts, set under **Operator Account** and **Agent Account** on the host's **Settings** tab:

| Account | Default name | For |
| --- | --- | --- |
| Operator | `ops` | You: SSH, Cockpit, the console and the laptop's login |
| Agent | `agent` | The coding agents, T3 Code and the virtual desktop; home `/home/agent` |

Separate accounts keep sessions apart, but they do not isolate data from an agent that can become root.

## Passwords

On a password hash field, F4 generates a password and stores its hash, and F5 hashes a password you type. berth keeps a generated password in its store, beside the profile, and `berth credentials NAME` shows it. For a berth server's host the server generates it and keeps it. The profile itself only stores hashes.

- An empty agent password locks password login for the agent.
- Turning off the agent's passwordless sudo requires an agent password.
- The operator uses sudo without a password unless **Operator passwordless sudo** is off. With it off, berth asks for the operator's password when it connects, until **Ask for sudo password** says otherwise.

## Agent privileges

`agent_privileges` in the profile, **Agent privileges** on the Settings tab:

| Level | The agent's sudo |
| --- | --- |
| `full` | Everything, without a password. For machines you can throw away |
| `limited` | `apt-get` and `apt` with `update`, `install`, `upgrade`, `dist-upgrade`, `full-upgrade` and `autoremove`, and `systemctl restart` of plugin services that run as the agent. New profiles start here |
| `none` | Nothing |

Under `limited` and `none` the agent cannot change SSH, Tailscale, the firewall, the operator's account or berthd.

<Callout type="warn" title="limited guards against accidents, not intent">
  What a package installs runs as root, so an agent that may install packages can become root if it tries. An agent with `full` can administer the whole host. Use a dedicated machine or VM either way.
</Callout>

A profile without the setting keeps what it had before the setting existed: `full`, or sudo with the agent's password when `agent_passwordless_sudo` is off.

## Logging in as the agent

On the host, switch from the operator to the agent:

```bash title="On the host"
sudo -iu agent
```

From your machine, `berth ssh HOST --agent` opens a shell as the agent, and the overview's **Terminal** switches between the two accounts with Space.

## Logging in to hosts

berth reaches a host over SSH, as the SSH user of the host's **Install** tab, `access.user` in the [profile](/docs/reference/profile#access-access). **Log in with** under the address says how, in `access.auth`:

| Method | `auth` | What berth gives ssh | Where |
| --- | --- | --- | --- |
| berth's key | `berth` | The key `berth` of its key ring, and no other. The default | Local and server |
| Another key | `key:NAME` | That key of the key ring, and no other | Local and server |
| Password | `password` | The password kept as the secret `ssh/HOST`, through berth's own askpass helper | Local and server |
| Your SSH | `ssh` | Your SSH configuration and agent, with berth's key offered after your keys | Local berth only |

A password never goes into a command line or an environment variable. berth is ssh's askpass helper itself and reads the password from the store when ssh asks. No other program is asked, so no password dialog of the desktop opens. Without a stored password berth's own logins fail and say so, and `berth ssh HOST` asks on the terminal. For an apply, berth writes the password to a private file that Ansible reads, and Ansible gives it to ssh through its own helper.

```bash
berth secret set ssh/studio          # the SSH password of studio
berth secret set sudo/studio         # its sudo password, if you want it kept
```

A host that berth reaches through `access.link`, such as a container, doesn't use a key.

### Keys

berth keeps SSH keys in its store, by name, sealed when the [store is encrypted](/docs/use/store#encrypt-it). The key `berth` always exists. berth writes a private half to `keys/NAME` in its data directory when ssh or Ansible needs it, and `berth inventory` names that file. Private halves never leave through the API or a command.

```bash
berth key                            # the keys, the hosts that use each, and what is pending
berth key new deploy                 # make an ed25519 key
berth key add deploy ~/.ssh/deploy   # take in a private key; - reads standard input
berth key show deploy                # the public half, for an authorized_keys
berth key remove deploy              # refused while a host logs in with it
```

berth takes any private key `ssh-keygen` reads, and refuses one with a passphrase, as nobody would be there to type it. With a berth server set, these commands act on the server's keys. The Settings tab of the home screen lists the keys, and Enter copies a public half.

### First contact

A machine berth did not set up doesn't take berth's key yet. Give it a password or a private key that works once:

```bash
berth key trust studio               # asks for the password without echo
berth key trust studio --key ~/.ssh/provider_key
```

berth tries the host's key first. If the host refuses it, berth logs in once with what you gave and adds the key to the SSH user's `~/.ssh/authorized_keys`. The other lines of that file stay as they are. Then berth checks that a login with the key works, and forgets the one-time credential. A host whose method was `password` logs in with berth's key from then on, unless you add `--keep-password`, which keeps the password as the secret `ssh/HOST`.

### Host keys

berth records each host's SSH host key in its store and gives ssh a known-hosts file of its own for each host, under `known_hosts/` of the data directory, written from the store. So a restored installation knows its hosts. The first login records the key. A key that changes later is refused:

```text
The SSH host key of studio is not the one berth recorded: the machine was set up again or replaced, or something is in between. If you know which, accept the new key with: berth key host studio --accept
```

`berth key host studio` shows the recorded key. When berth itself creates a host's machine again, it forgets the old key and records the new one without asking. When a profile of berth 0.4 is converted, a host keeps the key your `~/.ssh/known_hosts` has for its address.

### Rekeying

`berth key rotate` replaces the key `berth`, and `berth key rotate NAME` another one:

1. berth makes a new key and stores it beside the current one as pending.
2. On each host that takes the key, it logs in and adds the new key. Once a login with the new key works, it removes the old one.
3. A host that does not answer stays pending. berth offers it both keys until then, and an apply gives the operator both.
4. When no host is pending, the new key replaces the old one, which is deleted.

Running it again goes on where it stopped. With a berth server set, the rotation runs as a job on the server, and its output is shown as it comes.

### Sudo

`access.sudo` says whether the SSH user's sudo asks for a password: `none` or `password`. Left out, berth asks only when the operator has no passwordless sudo and the user is not root. berth asks for the password when it needs it, or takes the secret `sudo/HOST` if you keep it there. It reaches sudo on standard input.
