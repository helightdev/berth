A profile is a JSON document that describes one host. berth keeps it in its store and writes it from the set-up tabs. The fields below can also be edited by hand: write the profile to a file, change it and save it back.

```bash
berth profile studio > studio.json
berth profile studio --set studio.json
```

`--set -` reads the profile from standard input. berth checks it as the terminal UI reads a profile and saves it as it is. The profile of a berth server's host is saved on the server.

A profile can also stay in a file of its own. berth reads a host given as a path, such as `berth ./studio.json`, from that file and saves it there.

Settings of the Ansible role go under `ansible_vars`, and how berth reaches and installs the host under `builder`.

```json title="studio's profile (excerpt)"
{
  "hostname": "studio",
  "profile": "laptop",
  "operator_username": "ops",
  "operator_ssh_public_keys": ["ssh-ed25519 AAAA... you@workstation"],
  "agent_username": "agent",
  "agent_privileges": "limited",
  "target_disk_mode": "auto",
  "keyboard": "us",
  "ansible_vars": {
    "devbox_plugin_features": ["claude/cli", "codex/cli", "t3/server", "github/cli"]
  },
  "access": { "address": "studio.example.ts.net", "user": "ops", "auth": "berth" }
}
```

A profile written before the lists has one key in `operator_ssh_public_key` or `agent_ssh_public_key`. berth still reads it, and moves it into the list when the keys are next changed.

### The key of berth itself

Each berth makes an ed25519 key of its own the first time it needs one: the key `berth` of its [key ring](/docs/use/accounts#keys). It keeps the key in its [store](/docs/use/store). An installation restored from the store gets the same key back. The operator of a host takes it along with the keys in the profile, so the berth that set a host up can log in to it without a key of yours. That matters most for a [berth server](/docs/use/server), which has no keys until you give it some. During a [rotation](/docs/use/accounts#rekeying) the operator takes the new key as well.

`berth key show` prints the public half. To copy it, choose **This berth's SSH key** on the Settings tab of the home screen, or press `c` on the field of the same name on a host's Settings tab. With a berth server set, both copy the server's key.

Add the key as an SSH key at your cloud provider, and every machine you create there takes it. berth then logs in to a new machine without a key of yours. On a host set up some other way, add it to the operator's `~/.ssh/authorized_keys`.

Turn **This berth's SSH key** off in Accounts, or set `berth_ssh_key` to `false`, for a host that should only take the listed keys.

## Role settings (`ansible_vars`)

Any `devbox_` setting of the role. The ones the terminal UI edits:

| Setting | In berth | Default |
| --- | --- | --- |
| `devbox_plugin_features` | Features tab | `claude/cli`, `codex/cli`, `pi/cli`, `t3/server`, `github/cli` |
| `devbox_tools_*` (one per [category](/docs/reference/tools#tool-categories)) | Features tab | on |
| `devbox_install_playwright` | Features tab | on |
| `devbox_software_rendering` | Software graphics, Features tab | on |
| `devbox_geometry` | Desktop size, under Desktop on the Settings tab | `1600x900` |
| `devbox_bootstrap_ssh_cidr` | Recovery SSH CIDR, Settings tab | none |
| `devbox_harden_ssh` | SSH hardening, under Access on the Settings tab | on |
| `devbox_install_cockpit` | Cockpit web console, Features tab | on |
| `devbox_install_docker` | Docker on host, Features tab | on |
| `devbox_install_tailscale` | Tailscale, Install tab | on |

Others, such as `devbox_tailscale_serve`, the agent versions and the backup settings, are described where they are used. All defaults are in [`defaults/main.yml`](https://github.com/helightdev/berth/blob/main/ansible/roles/devbox/defaults/main.yml).

## Access (`access`)

Where the host is and how berth logs in to it. Every host has it. See [Logging in to hosts](/docs/use/accounts#logging-in-to-hosts).

<TypeTable
  type={{
    address: { type: 'string', description: 'Hostname, IP address or Host alias from ~/.ssh/config. A host with one opens on its overview.' },
    user: { type: 'string', description: 'The SSH user. Blank uses your SSH configuration.' },
    port: { type: 'string', description: 'The SSH port. Blank uses your SSH configuration.' },
    auth: { type: '"berth" | "key:NAME" | "password" | "ssh"', default: '"berth"', description: 'How berth logs in: its own key, another key of its key ring, a password kept as the secret ssh/HOST, or your own SSH configuration and agent with berth\'s key offered after them.' },
    sudo: { type: '"none" | "password"', description: 'Whether the SSH user\'s sudo asks for a password. Left out, berth asks only when operator_passwordless_sudo is off and the user is not root.' },
    link: { type: 'string[]', description: 'A command that connects to berthd instead of SSH, such as docker exec -i NAME berthd connect. A host with one needs no address.' },
  }}
/>

A profile of berth 0.4 kept these under `builder`:

| berth 0.4 | Now |
| --- | --- |
| `ssh_host`, `ssh_user`, `ssh_port` | `address`, `user`, `port` |
| `ssh_key` | `auth`: `key:NAME` |
| `ask_pass` | `auth`: `password` |
| `ask_become_pass` | `sudo` |
| `link` | `link` |

 berth converts stored profiles once, and reads a profile in a file in the new layout. The file keeps the old layout until you save it. A key file that `ssh_key` named becomes a key of the key ring, and the host logs in with it. If berth cannot read the file, the host logs in with `ssh`, and berth says so. A host without a key file logs in with `ssh`, which is what it did before.

## Beside the profile

berth keeps more of a host in its store, beside the profile:

| What | Holds | How to see it |
| --- | --- | --- |
| Generated passwords | The passwords F4 made for the host's accounts | `berth credentials HOST` |
| The machine's record | The [resource](/docs/deploy/resources) of a machine berth created for the host, with its provisioner and id | `berth instance HOST` |

`berth credentials` prints an account and its password to a line, and only to a terminal unless `--show` is given. For a berth server's host it asks the server, which keeps them. `berth remove HOST` forgets the profile and both of these at once. It refuses while berth knows of a machine it created for the host.

Secrets and registries a host gets are listed in the profile by name (`secrets`, `registries`). Their values stay in berth's store.
