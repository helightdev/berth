## The repository

| Folder | Holds |
| --- | --- |
| `cli/` | `berth`: the terminal UI, the commands and `berth serve` |
| `crates/` | Shared libraries: `berth-core`, `berth-api`, `berth-pty`, and `berth-tui`, the screens the terminal UI and the page share |
| `web/` | The page `berth serve --web` shows in a browser, built for WebAssembly. The docs build copies it to `/web` |
| `host/` | `berthd` and `box`, built static for hosts |
| `ansible/` | The devbox role |
| `plugins/` | The plugins that come with berth |
| `bootstrap/` | First-boot provisioning |
| `bin/` | `devbox.py` (release, seeds, ISO), `qemu.py`, `write-usb.sh` |
| `container/` | The desktop image, berth's own image, and the images and script for checks and tests |
| `docs/` | This site |
| `tests/` | Python tests, and the end-to-end tests in `tests/e2e/` |

## Build

```bash
rustup target add x86_64-unknown-linux-musl     # once
cargo build --release -p berth
cargo install --locked --path cli                # into ~/.cargo/bin
```

The build first makes `berthd` and `box` as static musl binaries and places them in the role's files. It then packs the provisioning source and embeds it in `berth`. It needs Python 3 for the packing.

A release build embeds release builds of `berthd`, `box` and the page. A development or test build (`cargo build`, `cargo test`) embeds quicker ones:

| Part | Profile | Built |
| --- | --- | --- |
| `berthd`, `box` | `host-dev` | Optimised for size, incrementally, with debug assertions |
| The page | `web-dev` | Optimised, without the link-time optimisation of `web` |
| berth itself | `dev` | Line numbers, no other debug information |

For a debugger, `CARGO_PROFILE_DEV_DEBUG=true` gives berth's own crates full debug information.

While changing the role or plugins, point berth at the checkout instead of the built-in copy:

```bash
berth config source "$PWD"
```

## Check

```bash
cargo test --locked
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests
.venv/bin/ansible-playbook -i localhost, ansible/site.yml --syntax-check
vale README.md docs/content/docs
```

Two of the Rust tests compare the API that berthd and `berth serve` describe with the committed documents in `docs/openapi/`. After changing a route, regenerate them. `BERTH_UPDATE_DOCS=1 cargo test` writes them.

## In containers

With Docker or Podman you need nothing else on your machine. `container/ci.sh` builds an image with Rust and its targets, Python with Ansible, and Vale. Everything runs in it. CI runs the same script.

```bash
container/ci.sh check              # what CI checks
container/ci.sh check clippy vale  # some of it
container/ci.sh e2e                # the end-to-end tests
container/ci.sh shell              # a shell with the toolchain, the checkout at /src
```

The checkout is mounted, and files are written as you. Cargo's downloads and the target directory stay in the volumes `berth-ci-cargo` and `berth-ci-target`, so later runs are fast. `container/ci.sh clean` removes them and the images.

The test host of the end-to-end tests is an Ubuntu container with SSH and an operator account. A profile is applied to it over SSH, with the role's tasks for the accounts, the plugins and berthd. The tests then use the host through berth's commands, berthd's API and `berth serve`. The desktop packages, toolchains and browsers are left out. The test host and the tests are on an internal network with no way out. Each run starts from a new host and removes it afterwards. After a failure the host's logs are in `build/ci/logs/`.

To run one module or one test case, name it: `container/ci.sh e2e e2e_serve.Roles`. The modules are listed in order in `tests/e2e/run.py`. A new one goes there, after the ones whose state it uses.

## The release archive

```bash
python3 bin/devbox.py release
```

writes `build/devbox-release.tar.gz` and `build/release.sha256`. The archive is deterministic for the same source files and uses an explicit allowlist: it never contains local host profiles, secrets, virtualenvs or build output. Host-specific installer images and seeds are private and must not be published.

## The docs

```bash
cd docs
npm install
npm run dev         # http://localhost:3000
npm run build       # static site in docs/out
```

The guide pages are MDX files in `docs/content/docs/(guide)`. The API reference is generated before every build from `docs/openapi/` by `docs/scripts/gather.mjs`. The terminal screenshots in `docs/public/screens/` come from `docs/scripts/screens.py`, which runs the built binary against an invented set-up and a throw-away container. See the comment at its top. Set `DOCS_BASE_PATH` when the site is served from a folder, such as `/berth` on GitHub Pages.

## Releases

GitHub Actions build on every push:

| Workflow | Does |
| --- | --- |
| CI | The checks above and the end-to-end tests, both with `container/ci.sh`, and Vale |
| Docs | The docs build, and publishing it to GitHub Pages from `main` |
| Build | The static `berth` for Linux x86_64 as artifact `berth-x86_64-linux`, the host programs as `host-programs-x86_64-linux`; the container image `ghcr.io/helightdev/berth`, tagged `edge` from `main` |

Pushing a `v*` tag also publishes a GitHub release with `berth-x86_64-linux.tar.gz`, its checksum file and `install.sh`. The image gets the version as its tag. `install.sh` installs the latest release.

## With the page for a browser

berth comes in two builds. The usual one has no page. The `web` feature adds the page `berth serve --web` shows, built from `web/` as WebAssembly and carried in the program (about 2 MB more):

```bash
rustup target add wasm32-unknown-unknown        # once
cargo build --release -p berth --features web
```

| Build | Release archive | Install script |
| --- | --- | --- |
| Usual | `berth-x86_64-linux.tar.gz` | the default |
| With the page | `berth-web-x86_64-linux.tar.gz` | `BERTH_VARIANT=web` |

`berth update` stays with the build it is. The container image is the one with the page. The docs build takes the page from `target/web-dist` for `/web`. It builds the page with the `web` profile, as a release does, by setting `BERTH_WEB_PROFILE=web`.
