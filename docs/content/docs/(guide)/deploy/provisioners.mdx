title: Provisioners
description: Have a plugin create the machine for a saved host on Docker, Incus or another platform, and look after the platform from its provisioner's page.

---

A provisioner creates the machine a host's profile describes, such as a container or a virtual machine. berth runs it and keeps a record of the machine in its store, as a [resource](/docs/deploy/resources). From then on the machine is an ordinary host. Some provisioners make other kinds of resources too, such as the [deployments](/docs/deploy/deployments) of the Docker plugin.

Plugins bring the types of provisioner, such as `incus/vm` or `docker/container`. Each provisioner you register is of one type and has a name of your own, such as `ovh-incus`. It works like a [registry](/docs/use/registries). Each keeps settings and secrets of its own. Register as many of one type as you have servers or engines.

A provisioner is also a place of its own, with a page that says whether the platform answers and lists what berth made there. The actions on that page come from the plugin, such as listing images or removing what berth left behind.

Each host has at most one machine made this way.

## Register a provisioner

See the types the plugins bring:

```bash
berth provisioner types
```

```text
docker/container     Docker container  · makes machine, deployment
incus/container      Incus container  · makes machine
incus/vm             Incus virtual machine  · makes machine
```

Register one under a name, with the values of its own arguments:

```bash
berth provisioner add ovh-incus incus/vm server=https://192.0.2.10:8443
berth provisioner add docker docker/container
```

Names take lowercase letters, digits, `-` and `_`, and start with a letter. The type stays as it was registered. To use another, register one under another name. See which provisioners you have, and whether each can be used here:

```bash
berth provisioner
```

```text
docker  Docker container (docker/container)
ovh-incus  Incus virtual machine (incus/vm)  · not usable: ovh-incus needs the secrets incus_client_cert, incus_client_key: berth secret set NAME
```

One that cannot be used says what to change, such as a [secret](#secrets) to set or a plugin to update. `berth provisioners` lists the same with what each asks for:

```text
ovh-incus                Incus virtual machine
  A KVM guest on an Incus server, set up from berth's cloud seed. The server needs KVM.
  · makes machines that set themselves up from the cloud seed
  · actions server, pools, images, networks
  · also start, stop, list
  · asks server
  · asks cpus (default 4)
  · secret incus_client_cert, not set
```

The listing is shortened here. A secret marked *not set* is required and has no value yet.

In the terminal UI, `a` on the **Provisioners** tab adds one. It asks for the name and then the type.

`berth provisioner remove NAME` forgets a provisioner, with its settings and its own secrets. berth refuses while it holds anything, so remove what it made first. The action `remove` on its page does the same.

### From an earlier version

berth before named each provisioner by its type and kept one set of settings for each type. When it starts, berth registers each type that has settings or made something under the name `PLUGIN-ID`, such as `incus-vm` for `incus/vm`, with those settings. What it made then names that provisioner. A type that was never used is not registered. The secrets stay where they are, and every provisioner of the type shares them.

## A provisioner's page

```bash
berth provisioner docker
```

```text
docker  Docker container

State     ready · Docker 27.5.1 answers at ssh://ops@192.0.2.10
Endpoint             ssh://ops@192.0.2.10
Engine               27.5.1
Runtimes             io.containerd.runc.v2, runc, sysbox-runc
Machines berth made  1
Settings  host=ssh://ops@192.0.2.10

Machines berth made with it
  studio-2         berth-studio-2  running · r-k3q7wz2m

Compose project berth made with it
  notes            notes  running · r-p5x2hd7a

Actions (berth provisioner docker run ACTION)
  Engine
    engine             Check the engine
    images             Images
    build              Build the image
  Storage
    volumes            Volumes berth made
    prune              Remove what berth left behind
  Create
    new-deployment     New compose project
  Set-Up
    settings           Settings
    remove             Remove provisioner
```

berth asks the provisioner how it is each time. The lines under the state are what it says, shown as they are.

| State | Means |
| --- | --- |
| `ready` | It answered. Its message says how it is |
| `unreachable` | It did not answer, as when the engine or server is down. The message says why |
| `unusable` | berth does not ask it: a secret or a setting is missing, or the plugin is of an older version |

What berth made is listed by kind, each with berth's id of the resource and the state the provisioner lists for it. One the provisioner lists with berth's labels, but that berth has no record of, is marked *berth has no record of it*. berth does not delete it. [Resources](/docs/deploy/resources) says how to look after each one.

### Settings

A provisioner's own arguments say where it is, such as the Incus `server` or the Docker `host`. berth keeps their values as the provisioner's settings, in its store:

```bash
berth provisioner ovh-incus run settings server=https://192.0.2.10:8443 project=lab
```

Every call to the provisioner uses them, and so does each machine made with it unless `berth provision` is given another value. The record of a machine keeps the values it was made with, and an empty setting is forgotten. While a setting it needs has no value, berth prompts for it before each action.

`berth provisioner NAME SETTING=VALUE…` asks another place this once, such as `berth provisioner ovh-incus server=https://192.0.2.11:8443`.

### Secrets

The plugin declares the secrets its provisioners need, such as `incus_client_cert`. berth gives each provisioner the secret of that name, which every provisioner of the type shares. One with secrets of its own is given those instead. Each is kept as the secret `provisioner/NAME/SECRET`, and `berth secret set` reads it from standard input:

```bash
berth secret set provisioner/ovh-incus/incus_server_cert < server.crt
```

The action `secrets` on the provisioner's page takes each in a hidden field. An empty value keeps what it has, and `-` forgets it. The Secrets tab of the terminal UI leaves them out. This way an Incus server that trusts another certificate of berth gets its own.

### Actions

```bash
berth provisioner docker actions
berth provisioner docker run images
berth provisioner docker run prune volumes=yes
```

In a terminal, `run` prompts for a required argument you leave out. It puts the action's question first, unless `--yes` is given. An action that only reads, such as `images`, answers at once. One that changes something runs as a job and shows its output as it comes. Only one such job runs at a time for a provisioner.

In the terminal UI, the **Provisioners** tab of the home screen (`2`) lists the provisioners, and `a` registers one. Enter opens a page, which lists the actions in their groups and what berth made there, by kind. Enter on an action shows its question and then a dialog for its arguments. A job's output fills a panel. An argument of several lines, such as a Compose file, keeps the line breaks of what you paste. Each shows as `⏎`. Enter on something berth made opens its [resource's page](/docs/deploy/resources#in-the-terminal-ui), and Esc comes back. The page of [`berth serve --web`](/docs/use/server#in-a-browser) has the same tab.

## Seed and apply

A provisioner sets up the new machine in one of two ways. The plugin chooses.

| Kind | The new machine | berth waits for | What the profile needs |
| --- | --- | --- | --- |
| `seed` | Boots with berth's [cloud seed](/docs/deploy/cloud) made from the profile and sets itself up | berthd to answer, up to 30 minutes. It then prints the machine's provision state | What `berth seed` needs. A provisioner that puts the release archive into the machine itself does without a `release_url` |
| `apply` | Starts with SSH and an account for berth | SSH to answer, up to 5 minutes. berth then applies the profile as `berth apply` does | An SSH user, `access.user` |

For an `apply` provisioner the account is the profile's SSH user. It takes berth's [own key](/docs/reference/profile#the-key-of-berth-itself) and the keys of the profile's operator. If that user's sudo asks for a password, set `BERTH_SUDO_PASSWORD` for the command, or apply later with `berth apply HOST`.

A provisioner may report the machine's address and SSH port. berth writes them to `access.address` and `access.port` of the profile, but only where those are empty. A machine just made has a new SSH host key, so berth forgets the host key it recorded for the host and records the new one at the first login.

A seeded machine whose address berth does not know is not waited for. berth says so and ends. The machine sets itself up on its own, and you set `access.address` to reach it.

### While berth waits

The first boot of a seeded machine installs everything and can take most of the 30 minutes. berth says what it can find out as it goes, and each thing only once. Lines that come from the machine start with `│`.

| What | When |
| --- | --- |
| The machine's state and address | When the provisioner reports a new one |
| The latest lines of the machine's console | Until SSH answers, from provisioners whose machines have `logs` |
| `SSH answers` | Once berth can log in |
| The first boot's state, its steps and the Ansible task it is at | After SSH answers, for a seeded machine |
| `berthd answers` | When the host is ready |
| `still waiting` and the time so far | After a minute without any other line |

```text
▸ studio-2: waiting for berthd to answer (up to 30 minutes)
▸ studio-2: its machine is running at 192.0.2.31
  │ [  OK  ] Started ssh.service - OpenBSD Secure Shell server.
✓ studio-2: SSH answers
  │ first boot: provisioning
  │ Installing Ansible
  │ Applying the role
  │ Ansible task 87: Install the desktop
… studio-2: still waiting, 12 minutes so far
  │ Ansible task 214: Configure the browser
  │ first boot: configured-needs-enrollment
✓ studio-2: berthd answers
```

Reading the first boot's log needs sudo on the machine. The seed gives the operator sudo without a password, so berth doesn't need one for it. An SSH user without such sudo sees the first boot's state only.

When the first boot fails, berth stops waiting at once and shows the last lines of its log. The machine tries again by itself every 10 minutes. berth hides the secrets in the seed, such as password hashes and the enrollment key, in every line it shows.

## Create the machine

<Steps>
<Step>

### Save the host

Make the profile as for any host. The provisioner works from the saved profile.

</Step>
<Step>

### Store the secrets

A provisioner that needs provider credentials lists them as secrets. Store them once:

```bash
berth secret set incus_client_cert < berth.crt
berth secret set incus_client_key < berth.key
```

berth refuses to start while a required secret has no value.

</Step>
<Step>

### Create it

```bash
berth provision studio-2 ovh-incus cpus=8
```

berth asks `Create a machine for studio-2 with Incus virtual machine (ovh-incus)? [y/N]`. `--yes` answers it. Arguments are `NAME=VALUE`. An argument that is required and has no default is asked for in a terminal when you leave it out. The others take their defaults.

The output of the provisioner and of the set-up follows as it runs. berth ends when the host answers, or says what failed.

</Step>
</Steps>

In the terminal UI, choose **Create a machine** under **How To Install** on the host's Install tab. The arguments of the provisioner are spread over the tabs:

| Tab | Shows |
| --- | --- |
| Install | **Provisioner**, a choice like any other. Space or Enter switches to the next one, and → chooses from the suggestions. Under it the required arguments, marked `*` |
| Settings | Under **Machine**, the resources it has, such as CPUs, memory and disk. Under **Provisioner Options**, its other arguments |
| Run | **Create machine**, and every problem |

The first provisioner is chosen when the list arrives. There is no **Host profile** row. A created machine is always a `cloud` host. berth writes that into the profile before it creates the machine, on the command line as well. Enter on an argument changes it. A missing secret is a problem of the Install tab, and a bad resource value one of the Settings tab. **Create machine** on the Run tab asks once before it saves the profile and starts, and does not start while a problem is listed. The output is shown as it runs. The page of [`berth serve --web`](/docs/use/server#in-a-browser) has the same tabs.

Only one thing runs at a time for a host. A second command for the same host is refused until the first ends.

## Look after the machine

The machine is a [resource](/docs/deploy/resources) of the kind `machine`. `berth instance HOST` shows it by the host's name, as `berth resource ID` does:

```bash
berth instance studio-2
```

```text
r-k3q7wz2m  machine studio-2 of ovh-incus
State      running
Made as    berth-studio-2
Host       studio-2
Address    192.0.2.31
Created    2026-11-12T20:14:03Z
Asked      2026-11-13T08:02:11Z
Arguments  cpus=8 disk=60GiB image=ubuntu/26.04/cloud memory=8GiB pool=default project=default server=https://192.0.2.10:8443

Actions (berth resource r-k3q7wz2m run ACTION)
  start              Start
  stop               Stop
  change             Change
  remove             Delete the machine

Its log: berth resource r-k3q7wz2m logs [--follow]
```

The state comes from the provisioner each time you ask. A machine the platform no longer has is `missing`, and its record stays until you delete it through berth ([States](/docs/deploy/resources#states)).

`berth instance HOST start` and `stop` work only when the provisioner offers them. The actions above say which. The Run tab shows the machine's state and a **Start machine** and **Stop machine** row in the same cases, whatever install method is chosen.

## When it fails

What happens depends on how far it got.

| It failed | What is left | To go on |
| --- | --- | --- |
| Before the provisioner gave an id | A record with a token, and perhaps a machine | `berth provision` again with the same provisioner. The provisioner finds the machine by the token and does not make a second one |
| After it gave one, such as a boot that did not finish or a failed apply | The machine and its record. The message says so | Fix the cause and wait, or `berth apply HOST` for a failed apply. `berth resource ID remove` deletes the machine to start again |

A record without a machine is shown with a problem that says creating it did not end. Asking for a different provisioner while it exists is refused. `berth resource ID remove` then forgets the record only. A machine the provisioner made anyway is not deleted.

## Delete the machine

```bash
berth instance studio-2 destroy
```

berth asks you to type the host's name. `--yes` skips that. `berth resource ID remove` does the same and asks yes or no. It runs the provisioner's `destroy` with the id it kept, never another, and then removes the record. A machine that is gone already counts as deleted. If deleting fails, the record stays so you can try again.

The profile stays. The host's node on the tailnet is not removed. Remove it in the tailnet's admin console.

Deleting needs the provisioner's plugin and its required secrets. Removing a host with `berth remove` is refused while its machine exists. Delete the machine first.

## With a berth server

With a [berth server](/docs/use/server) set, the server creates the machines. Its commands and the set-up tabs go to the server, and the provisioner runs on the server's machine with the server's plugins, secrets and provisioner settings. Creating and deleting a machine are jobs there of the subject `resource:ID`, named `create` and `remove`, and their output follows as for an apply. An action of a provisioner that changes something is a job there too, of the subject `provisioner:NAME`.

| What | Role |
| --- | --- |
| The list, the types, a provisioner's page and its actions | `view` |
| Registering and removing a provisioner | `admin` |
| An action of a provisioner | Its own: `admin` for one that changes something, `view` for one that only reads, unless the plugin says otherwise |
| Looking at what it made | `view` |
| Creating, changing, starting, stopping and deleting what it made | `admin` |

[Resources](/docs/deploy/resources#with-a-berth-server) lists the operations with their roles.

A server with `serve_setup off` does not take set-up over the network, only on its own socket ([Closing set-up](/docs/extend/serve#closing-set-up)).

## Credentials stay where berth runs

Provider credentials are berth secrets, shared by a type or a provisioner's own. They are kept in a file that only its user can read, on the machine that runs berth. With a server, that is the server. berth gives a provisioner only the secrets its plugin names, under those names, on its standard input. berth does not write the request anywhere. Lines of the provisioner's output that contain one show `[secret]`.

<Callout type="warn" title="A provisioner is a program that runs as you">
  It runs with the rights of the user berth runs as, and it gets the credentials it names. Install only provisioner plugins you trust.
</Callout>

## The plugins that come with berth

The documentation site does not show the guides of these plugins. Each is a `guide.md` beside the plugin's `package.json`, under `plugins/` in the berth source, and lists every argument and the limits.

### Docker

A provisioner of the type `docker/container` makes an Ubuntu 26.04 container with systemd and an SSH server on the local Docker or on the engine named by `host`, such as `ssh://ops@192.0.2.10`. berth applies the profile to it over SSH. The container is named `berth-HOST` and has the labels `berth-host` and `berth-instance`. It offers `start`, `stop`, `change`, `logs` and `list`, and takes no secrets.

The same provisioner runs Compose projects on that engine as [deployments](/docs/deploy/deployments).

For an engine at `ssh://user@address`, the provisioner only sets `DOCKER_HOST`, and Docker starts the system's `ssh` with your own SSH configuration and known hosts. It does not use berth's recorded host key of that server or berth's key. The address has to be in your own known hosts, so log in once with plain `ssh` first. The account's key has to be one your `ssh` offers, from your configuration or agent. ssh cannot ask for a password.

| Action | Does |
| --- | --- |
| `engine` | Says the engine's version, its runtimes and how many machines berth made there |
| `images` | Lists the engine's images with their sizes |
| `volumes` | Lists the volumes berth made, and whether a container uses each |
| `build` | Builds the image the plugin brings ahead of the first machine |
| `prune` | Removes the plugin's images of older versions that no container uses. With `volumes=yes` it also removes the volumes berth made that no container uses, with the agent's work in them |

The container runs privileged by default. With `runtime=sysbox` it runs under [Sysbox](https://github.com/nestybox/sysbox) instead, which the Docker host needs to have. Read the limits in `plugins/docker/guide.md` before you use an engine that others share. In the container Chromium uses its setuid sandbox helper, as the [self-test](/docs/reference/on-the-host#the-self-test) describes.

```bash
berth provision studio-2 docker runtime=sysbox
```

### Incus

A provisioner of the type `incus/vm` makes a virtual machine, and one of `incus/container` a system container, on an Incus server. Both are set up from the cloud seed, and the plugin puts the release archive into the machine. The profile does without a `release_url`. They offer `start`, `stop`, `change`, `logs` and `list`. In a container Chromium uses its setuid sandbox helper, and in a virtual machine a user namespace, as the [self-test](/docs/reference/on-the-host#the-self-test) describes.

berth talks to the Incus API over HTTPS. `server` is required, as a setting or for each machine. Incus must trust a certificate of berth, which you store as the secrets `incus_client_cert` and `incus_client_key`. A provisioner may have its own instead. The secret `incus_server_cert` is optional and pins the server's own certificate. `plugins/incus/guide.md` shows how to make and trust the certificate.

Their actions only read: `server` says the server's version and whether it trusts berth, `pools` how full each storage pool is, `images` the images the server keeps, and `networks` its networks. The page offers the server's pools and networks for a machine's `pool` and `network`.

```bash
berth provisioner add ovh-incus incus/vm server=https://192.0.2.10:8443
berth provision studio-2 ovh-incus
```
